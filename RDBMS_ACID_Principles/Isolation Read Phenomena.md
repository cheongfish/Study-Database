# 트랜잭션 격리 수준과 읽기 현상

## 1. 트랜잭션 격리 수준 (Isolation Levels)

트랜잭션의 **격리 수준(Isolation Level)** 은 동시에 실행되는 트랜잭션 간의 **데이터 일관성을 유지하는 방법**을 결정하는 요소입니다.

### 1.1 격리 수준 개요

| 격리 수준 | 설명 | 발생 가능 문제 |
|-----------|--------------------------------------------------|------------------|
| **Read Uncommitted** | 다른 트랜잭션의 커밋되지 않은 데이터를 읽을 수 있음 | Dirty Read |
| **Read Committed** | 커밋된 데이터만 읽을 수 있음 | Non-Repeatable Read |
| **Repeatable Read** | 같은 트랜잭션 내에서 같은 데이터를 여러 번 읽어도 동일한 결과 유지 | Phantom Read |
| **Serializable** | 모든 트랜잭션이 직렬화되어 실행됨 | 성능 저하 |

각 수준은 동시성(Concurrency)과 데이터 일관성(Consistency) 간의 **트레이드오프**를 포함하고 있습니다.

## 2. 읽기 현상 (Read Phenomena)

읽기 현상(Read Phenomena)은 트랜잭션 격리 수준에 따라 발생하는 다양한 데이터 불일치를 설명합니다. 이를 방지하기 위해 격리 수준을 적절히 설정해야 합니다.

### 2.1 Dirty Read (더티 리드)

- **정의**: 한 트랜잭션이 **커밋되지 않은 데이터**를 읽는 경우 발생.
- **문제점**: 만약 원본 트랜잭션이 롤백되면, 읽은 데이터는 무효가 됨.
- **예시**:
  1. 트랜잭션 A에서 `UPDATE` 실행 후 커밋하지 않음.
  2. 트랜잭션 B에서 이 데이터를 조회하여 사용함.
  3. 이후 트랜잭션 A가 롤백하면, 트랜잭션 B는 잘못된 데이터를 사용한 상태가 됨.
- **해결 방법**: `Read Committed` 이상의 격리 수준 사용.

### 2.2 Non-Repeatable Read (비반복 읽기)

- **정의**: 동일한 쿼리를 반복 실행할 때, **중간에 다른 트랜잭션이 데이터를 변경**하여 결과가 달라지는 경우.
- **문제점**: 같은 트랜잭션 내에서 같은 데이터를 읽었는데도 값이 달라질 수 있음.
- **예시**:
  1. 트랜잭션 A가 특정 데이터를 조회 (`SELECT * FROM accounts WHERE id = 1`).
  2. 트랜잭션 B가 같은 데이터를 수정하고 커밋 (`UPDATE accounts SET balance = 500 WHERE id = 1`).
  3. 트랜잭션 A가 동일한 `SELECT` 실행 → 변경된 값(500)이 반환됨.
- **해결 방법**: `Repeatable Read` 이상의 격리 수준 사용.

### 2.3 Phantom Read (팬텀 리드)

- **정의**: 한 트랜잭션에서 특정 조건을 만족하는 데이터를 조회한 후, **다른 트랜잭션이 데이터를 추가, 삭제 또는 수정**하여 결과가 달라지는 경우.
- **문제점**: 범위 기반 쿼리 (`SELECT * WHERE 조건`) 실행 시 데이터가 동적으로 변화할 수 있음.
- **예시**:
  1. 트랜잭션 A가 `SELECT * FROM employees WHERE salary > 5000` 실행.
  2. 트랜잭션 B가 새로운 직원 데이터를 추가 (`INSERT INTO employees VALUES (...)`).
  3. 트랜잭션 A가 동일한 쿼리 실행 → 새로운 데이터가 포함되어 다르게 반환됨.
- **해결 방법**: `Serializable` 격리 수준 사용.

### 2.4 Lost Update (손실된 업데이트)

- **정의**: 두 개의 트랜잭션이 **동일한 데이터를 수정**할 때, 나중 트랜잭션이 이전 트랜잭션의 변경 사항을 덮어씌우는 현상.
- **문제점**: 데이터 무결성이 심각하게 훼손될 수 있음.
- **예시**:
  1. 트랜잭션 A가 `UPDATE accounts SET balance = balance - 100 WHERE id = 1` 실행 후 커밋하지 않음.
  2. 트랜잭션 B가 동일한 행을 업데이트 (`UPDATE accounts SET balance = balance - 200 WHERE id = 1`).
  3. 이후 트랜잭션 A와 B가 순차적으로 커밋되면서 하나의 변경 사항이 사라짐.
- **해결 방법**: 적절한 **락(Lock)** 또는 `Serializable` 격리 수준 사용.

## 3. 트랜잭션 격리 수준과 읽기 현상의 관계

| 격리 수준 | Dirty Read 방지 | Non-Repeatable Read 방지 | Phantom Read 방지 |
|-----------|-----------------|-------------------------|------------------|
| Read Uncommitted | ✗ (발생 가능) | ✗ (발생 가능) | ✗ (발생 가능) |
| Read Committed | ✓ (방지됨) | ✗ (발생 가능) | ✗ (발생 가능) |
| Repeatable Read | ✓ (방지됨) | ✓ (방지됨) | ✗ (발생 가능) |
| Serializable | ✓ (방지됨) | ✓ (방지됨) | ✓ (방지됨) |

## 4. 정리

- **격리 수준**을 올릴수록 동시성(Concurrency)은 낮아지고, 데이터 일관성(Consistency)은 향상됨.
- **Dirty Read**는 `Read Committed` 이상에서 방지 가능.
- **Non-Repeatable Read**는 `Repeatable Read` 이상에서 방지 가능.
- **Phantom Read**는 `Serializable` 수준에서만 완전히 방지됨.
- **Lost Update**는 `Serializable` 또는 적절한 잠금 메커니즘을 통해 방지 가능.

격리 수준을 선택할 때는 **데이터 무결성과 성능 간의 균형**을 고려해야 합니다.
